# Releasing Labely

A pushed version tag *is* the release (ADR-0039): it publishes a public GitHub release and
store artefacts, and it cannot be quietly undone once people download it. So the work before
the tag — one consistent version everywhere, a correct API version, a green local build — is
the part that matters, and the tag itself waits for the user's explicit yes.

Source of truth: `docs/releasing.md`. Background: `docs/adr/0038-desktop-packaging.md`,
`docs/adr/0039-store-builds-and-releases.md`, `docs/adr/0040-phase-6-close-out.md` (version
codes). Re-read `docs/releasing.md` if anything below seems out of date.

## How a tag becomes a release

- `.github/workflows/release.yml` (generated by dist from `dist-workspace.toml`) runs on a
  pushed tag matching `**[0-9]+.[0-9]+.[0-9]+*`, e.g. `v0.2.0`. On pull requests it only runs
  `dist plan`.
- A suffix (`v0.2.0-rc.1`) makes a GitHub pre-release.
- It calls three reusable workflows: `release-studio.yml` (studio via `cargo xtask package`),
  `release-mobile.yml` (Android AAB/APK, iOS archive/IPA), and, after publishing,
  `release-checksums.yml` (`SHA256SUMS` over every file). Studio and mobile also have
  `workflow_dispatch` and path-filtered PR triggers, so they can be test-run without a tag.
- Every signing secret is optional; without them the run is green but unsigned and says so
  in a notice. Secret names are in `docs/releasing.md`.

## Checklist

Work through it in order and tell the user the result of each step.

### 1. Pick the version

Ask the user for the version if they did not give one. Show the current one
(`[workspace.package] version` in `Cargo.toml`) and the existing tags (`git tag --sort=-v:refname | head`).
If there are no tags yet, `docs/releasing.md` says the first release should be a pre-release
(`-rc.1`), because the release workflow has never run end to end.

The tag must be exactly the `Cargo.toml` version, because the mobile builds read the file, not
the tag. So a first release asked for as "0.2.0" is bumped to `0.2.0-rc.1` and tagged
`v0.2.0-rc.1`. Never bump to `0.2.0` and then tag an rc: the version and the tag must agree.

### 2. Bump the version in both places

- `Cargo.toml`: `[workspace.package] version`. Every crate, the studio packages and the
  Android app read it from there; the Android version code is derived, so do not edit Gradle.
  The formula in `mobile/android/app/build.gradle.kts` (ADR-0040) is
  `(major·1 000 000 + minor·1 000 + patch)·100 + stage`, where stage is 99 for a release and
  the rc number for a pre-release. Examples: `1.2.3` → `100200399`, `1.2.3-rc.4` → `100200304`,
  `0.2.0` → `200099`, `0.2.0-rc.1` → `200001`. Compute it from the formula when you quote it;
  don't pattern-match the 1.x example.
- `mobile/ios/Labely/Labely.xcodeproj/project.pbxproj`: every `MARKETING_VERSION = …;` line
  (there are two). An xtask test compares them with `Cargo.toml`.
- Let cargo refresh `Cargo.lock` (any build does it) and commit it with the bump.

There is no CHANGELOG file; the GitHub release is generated by dist. If the user wants notes,
draft them from `git log <last-tag>..HEAD --oneline` (or the whole history for a first release)
and offer them for the release body.

### 3. API_VERSION and schema hash

`API_VERSION` in `crates/core/src/lib.rs` is the command-API version agents see; it is pinned
with the schema hash in `crates/core/tests/it/schema.rs` (`api_version_matches_schema_hash`).
Bump it at most once per release, and only if command schemas changed since the last tag:

```sh
git diff <last-tag>..HEAD --stat -- crates/core/src/commands crates/core/tests/it/schema.rs crates/core/src/lib.rs
cargo xtask schema-hash
```

If schemas changed and `API_VERSION` was not bumped yet in this cycle, follow AGENTS.md
"Schema changes" (bump, paste the hash, `INSTA_UPDATE=always cargo test -p labely-core`).
Ask the user before bumping, since it signals a breaking API change to agent integrations.

### 4. Verify locally

```sh
cargo xtask ci 2>&1 | grep -E "error|FAILED|failed|test result: FAILED|^ok|warning: unused" | head -40
```

This catches a version mismatch, a stale schema hash, and the dist `uses: $/` regression
(`cargo test -p xtask`). Optionally build the packages the way CI does (all in
`docs/releasing.md` "Local release builds"): `cargo xtask package`,
`dist build --artifacts=local --target <triple>`, the Gradle `:app:bundleRelease
:app:assembleRelease`, and the unsigned `xcodebuild archive`. Filter their output.

### 5. Merge to main

The bump goes through a normal PR to `main` (commit and PR only when the user asks; use their
usual flow). The tag must point at a commit on `main` whose `Cargo.toml` already has the new
version: the mobile builds read the file, not the tag.

### 6. Tag and push — only after explicit confirmation

Before creating or pushing anything, show the user exactly what will happen and wait for a
clear yes:

> Ready to release **v0.2.0-rc.1** (pre-release) from `main` at `<short sha> <subject>`.
> This runs: `git tag v0.2.0-rc.1 && git push origin v0.2.0-rc.1`, which publishes a public
> GitHub release with CLI, studio and Android files. Go ahead?

Check first that `git rev-parse HEAD` is the merged bump on an up-to-date `main` and that the
tag equals `v` + the `Cargo.toml` version. A pushed tag that later needs fixing means deleting
a public release, so a mismatch is worth stopping for. Never push a tag on your own initiative,
even if an earlier message said "release it" in general terms.

### 7. Watch the run and finish by hand

- Follow it: `gh run list --workflow release.yml --limit 3`, then `gh run watch <id>`.
- Read the notices; unsigned macOS, Android or iOS builds are reported there. Tell the user
  which packages are unsigned before they announce the release.
- Store builds are not uploaded automatically: download the `store-android` and `store-ios`
  artefacts (`gh run download <id> -n store-android -n store-ios`) and tell the user to upload
  the AAB in the Play Console and the IPA with Transporter. Without the Android secrets the
  AAB is unsigned; without the Apple secrets there is no IPA.
- The shell/PowerShell installers download from the release, so they fail while the
  repository is private; mention it if it applies.
- Checking a download: `sha256sum --check --ignore-missing SHA256SUMS`.

## Changing the release workflow

Never hand-edit `release.yml` beyond the known fix: change `dist-workspace.toml`, run
`dist generate`, then change the three `uses: $/.github/workflows/` lines to
`uses: ./.github/workflows/` (dist 0.34.0 bug; `cargo test -p xtask` checks it).
